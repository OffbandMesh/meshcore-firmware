### The one line-ending artifact, and the method that found it

`variants/minewsemi_me25ls01/platformio.ini` reports as a **single 333-line whole-file conflict** — our
lines 1–190 against theirs 192–332 — which makes it look like the heaviest variant file in the set. It is
not. **Upstream's blob is CRLF-terminated and ours is LF**, so git sees every line as changed.

`[verified: git cat-file blob <sha> | tr -cd '\r' | wc -c → ours 0, theirs 141. Audited the same way across
all 30 conflicting files: this is the ONLY mismatch; the other 29 are LF on both sides.]`

⚠ Method note, because two weaker tests gave two wrong answers before this one: `git show <rev>:<path>`
applies the checkout smudge filter and reports CRLF for files whose stored blob is LF, and
`grep -qc $'\r$'` silently matches every line under MSYS. **Only `git cat-file blob` reads the bytes as
stored.** Anyone re-deriving this must use `git cat-file`.

**Resolution consequence:** normalize that one file to LF *first*, then merge. The real diff is ~156 lines
with **6 envs on each side** `[verified: grep -c '^\[env:']`, which drops it from Group B's largest file to
one of its smaller ones.

### Group C — prefs / CLI core: `CommonRadioPrefs` (3 files, 17 hunks / 486 lines) · **🔴 HIGH**

`examples/companion_radio/NodePrefs.h` (5/242) · `src/helpers/CommonCLI.cpp` (8/183) ·
`src/helpers/CommonCLI.h` (4/61)

The governing item of this update. Upstream introduced `CommonRadioPrefs` — a new abstract interface
combining `ConfigSerializer` with a new `KeyValueStore` — and **moved 14 CLI handlers out of
`CommonCLI.cpp` into `CommonRadioPrefs.cpp`** with identical names and identical validation ranges. They
were moved, not deleted: `CommonCLI::handleCommand` now dispatches to
`_prefs->getRadioPrefs()->handleCommand()` first, then `_board->handleCommand()`, then the original chain
`[verified: upstream src/helpers/CommonCLI.cpp:183-192]`.

**Resolution:**
1. Adopt upstream's `CommonRadioPrefs` / `DynamicConfigSerializer` / `KeyValueStore` structure and the new
   dispatch order — it is where the rest of 1.18.0 calls through.
2. Implement the interface on our prefs classes: **11 pure-virtual getter/setter pairs × 2 classes**
   (`NodePrefs::RadioPrefs` and `CommonCLI`'s prefs).
3. Add a `getCustom()` accessor returning a `KeyValueStore*`, which Group E's role wiring needs.
4. Keep every Offband-only config key in `structure()`. Verify by key-count before and after, not by eye.
5. **Prefs-record safety is not at risk here and must not be re-litigated.** `ConfigSerializer` is a keyed
   token serializer, so added fields are added keys; `DataStore.cpp` is **absent from the entire delta**;
   and `src/helpers/prefs/PrefsLayout.h` only ever detects **pre-1.17.0 flat binary records**, which 1.18
   cannot change. It fails closed by design. This is the one place where the 1.17.0 cycle's hardest problem
   (#627) does **not** recur.
6. Upstream also fixes a `ConfigSerializer` parser bug where a key containing a digit makes `loadSerial`
   fail and prefs stop reloading. **0 of our keys contain a digit**, so we are not exposed; take the fix as
   a footgun removal.

### Group D — FEM/LNA access model (2 conflicting files, 3 hunks / 93 lines; 2 more silent in Group J) · **Medium — the decision is pre-settled**

`variants/heltec_v4/HeltecV4Board.cpp` (2/83) · `variants/heltec_t096/T096Board.h` (1/10) ✓

Upstream **deleted the three `MainBoard` virtuals** (`setLoRaFemLnaEnabled`, `canControlLoRaFemLna`,
`isLoRaFemLnaEnabled`) and made FEM variant-local and non-polymorphic: in 1.18 `T096Board` and
`HeltecV4Board` declare those methods **private and non-virtual**, `canControlLoRaFemLna()` is gone
entirely, and only each variant's own `handleCommand` calls them, persisting via
`setByKey("fem_rxgain", …)` with `attachDynamicPrefs()` applying the stored value at boot.

**We use them polymorphically in 15 files** — all four role examples, `src/MeshCore.h`, `CommonCLI.cpp`,
`OffbandConfigProtocol.h` (the fork-private capability registry) and 8 variant files including
`heltec_rc52`.

**Resolution, settled by the owner's standing rule that a base update drops no feature or core capability:
keep ours.** Re-declare the three virtuals on `MainBoard` in `src/MeshCore.h` (Group K), keep our 15 call
sites, and restore the public virtual half in each variant header. This is work, not a decision.

Why ours is a runtime *query* and not a build flag, verified: `variants/heltec_v4/LoRaFEMControl.cpp:23-38`
probes `P_LORA_KCT8103L_PA_CSD` at boot — LOW on a V4.2 (R4 pull-down, GC1109, no LNA control), HIGH on a
V4.3 (R33 pull-up, KCT8103L, controllable). **Two units of the same model running the same image differ by
a resistor strap**, so a capability-advertising protocol needs the question answerable at runtime from
shared code.

**Also take upstream's good part:** their per-variant `handleCommand` guards
`get/set radio.fem.rxgain` on `isLnaCanControl()` and replies `"Error: unsupported"`. Our
`CommonCLI.cpp:1311-1324` and `:1647-1652` already do exactly this via `_board->canControlLoRaFemLna()`
`[verified]`, so the two agree on behaviour — keep ours, and keep it reachable from the shared CLI.

⚠ Five boards are **ours alone** — `heltec_rc52`, `heltec_rcc6`, `meshsmith_photon_esp32c6`,
`meshsmith_photon_nrf52`, `qcc_badge`. Upstream has no such files, so they never conflict and never receive
upstream's port. We write both halves for them ourselves.

### `FIRMWARE_VER_CODE` — the headline collision, and it resolves (part of Group E)

Measured independently for this plan, not taken from a prior report:

| | Value | Source |
|---|---|---|
| Offband today | **22** | `examples/companion_radio/MyMesh.h:32` |
| Upstream 1.17.0 (our base) | **13** | `727fc051:examples/companion_radio/MyMesh.h:8` |
| Upstream 1.18.0 | **14** | `81dbae59:examples/companion_radio/MyMesh.h:7` |

**We did not collide by taking a number — upstream's numbering walked into a range we had already spent.**
`MyMesh.h:32` records the allocations: 18 (#508, second caps byte at offset 84), 19 (#510, caps2 0x01
NOTIFY_SCOPE), 20 (#509, caps2 0x02 BUTTON_MATRIX), 21 (#542, caps2 0x04 INDICATORS), 22 (#611, caps2 0x08
PKT_HASH). Upstream only defined 14 on 2026-10-15, gating `CMD_RUN_CLI_COMMAND 66` and
`RESP_CODE_CLI_REPLY 29` on "v14+".

**Resolution: keep 22. Do not move to 14.** Our client's own gates are keyed on our allocations — Block
≥ 15, Caplog ≥ 17, PktHash ≥ 22 — so lowering the number breaks every Offband client. And 22 ≥ 14 is
*correct* after this merge, because the merge delivers the actual v14 obligations: Group C brings
upstream's `CommonCLI` dispatch and `CMD_RUN_CLI_COMMAND 66`, and both 66 and `RESP_CODE_CLI_REPLY 29` are
**free on our side** `[verified: our commands are 0xC1/0xC3/0xC4/0xC5/0xC6; upstream's max is 66]`.

⚠ **The verification obligation this creates.** "22 ≥ 14" is only honest if 66 and 29 actually work.
Confirm at resolution that `CMD_RUN_CLI_COMMAND` and `RESP_CODE_CLI_REPLY` are implemented and reachable,
not merely that the number is high enough.

⚠ **And the exposure that exists today, before this merge.** We ship 22 right now while implementing none
of upstream's v14 features, because at our 1.17.0 base nothing upstream claimed 14. Any stock client built
against 1.18.0 reads our 22 as "v14+ present" and will offer the CLI path. **That is a live condition this
base update closes, not one it creates** — which is an argument for the update, not a risk of it. The
client side is tracked at
[OffbandMesh/meshcore-client#857](https://github.com/OffbandMesh/meshcore-client/issues/857); the
structural fix for the whole registry is
[#514](https://github.com/OffbandMesh/meshcore-firmware/issues/514), still open — a prose table in a header
comment cannot prevent this class of collision, and this is the second release in which it has mattered.

### Group H — `NRF52Board` (2 files, 3 hunks / 44 lines) · **Medium** ✓

`src/helpers/NRF52Board.h` (2/32) ✓ · `src/helpers/NRF52Board.cpp` (1/12) ✓

**On that last row — bounded, and the bound is what matters.** Our three retained-memory consumers each
validate their own magic and fall back to fresh defaults: SafeBoot `PersistedState` (`src/SafeBoot.cpp:158`,
`0x5AFEB007`), the CrashLog ring header (`CrashLog.cpp:123`, `0xCAFEF00D`) and the CrashLog boot counter
(`0xB007C001`). **Worst case is a one-time loss of the boot counter, the crash ring and the SafeBoot backoff
on the first boot after the update — detected and logged, never silent corruption.** Whether the layout
actually shifts is a link-time question answerable only by a map-file diff, and the answer cannot make the
outcome worse than that bound. Worth naming anyway: a crash-survival log that resets on firmware update
loses exactly the window you want right after an update.

## 5. Rollback

The integration branch is disposable: `git worktree remove` + `git branch -D` returns to `firmware-base`
with nothing lost, and nothing is pushed until the branch builds green. Per-group commits mean a single bad
resolution reverts without unwinding the merge. No device is touched until the hardware gate, and no
prefs-record migration is introduced by this update (Group C, item 5), so there is no on-device data
rollback to design — the single largest difference from the 1.17.0 cycle.

## 6. Not covered here

- **The `MACThenDecrypt` stack buffer overflow.** `src/Utils.cpp:157-184` passes
  `src_len - CIPHER_MAC_SIZE` into `decrypt()` with no block-alignment check; `decrypt()` rounds
  non-aligned input up to a 16-byte AES block and can write up to 8 bytes past the caller's stack buffer.
  Three call sites pass packet-derived lengths into stack buffers — `src/Mesh.cpp:158`, `:215`, and `:242`,
  the group-channel path. **Present in every shipped Offband image.** Upstream's fix (`9c9a2ba2`, refined by
  `b74ba545`) is in **1.18.0 only — NOT in 1.17.1**
  `[verified: git merge-base --is-ancestor 9c9a2ba2 d9296435 → false; → 81dbae59 true; → origin/firmware-base false]`,
  so taking a patch release does not remediate it. It arrives with this base update by default. **Pulling it
  out as a standalone security patch ahead of this branch is an owner decision** — #613 puts routine
  cherry-picking out of scope, so it needs an explicit call either way. Proposed separately.
- **Adopting `MainBoard::loop()` as the watchdog feed path** (Group H) — better than ours, and a follow-up.
- **Client work.** The client must stay stock-compatible with Offband features additive on top, and 1.18
  moves upstream's stock-facing surface (node discovery, sensor telemetry push, `tz.offset`,
  `reboot`/`poweroff`/`shutdown`, WiFi settings, `CMD_RUN_CLI_COMMAND 66` / `TXT_TYPE_CLI_COMMAND 3`).
  **1.18 does not break the client's stock path today** — our guards are length-based, so an 82-byte stock
  frame returns null and every Offband gate is correctly false, and an unrecognised `txt_type` is logged and
  dropped `[verified: meshcore_connector.dart:6486-6510, :7514-7519]`. The gap is that nothing watches for
  that stopping being true. Lives in `OffbandMesh/meshcore-client`, already has a session on it.
- **Upstream features arriving inert** — Ethernet transport, `ExternalWatchdogManager`, LR2021, the 38 new
  envs. Whether Offband adopts any is out of scope for this branch.
