## 0. In plain terms, before the detail

MeshCore 1.18.0 does one big structural thing and carries one thing we need.

**The structural change: upstream reorganized how a board exposes its own hardware features.** Until now, if a board could control its radio front-end amplifier, the shared code could simply ask it — "can you do this?" — and any board could answer. Upstream removed that question. In 1.18 each board instead handles its own text commands privately, and the shared code no longer knows the feature exists.

That is a reasonable choice at upstream's scale, and a bad one for us, because Offband advertises what a board can do over the companion protocol so the app can show or hide controls. And the answer genuinely varies **per physical unit, not per board model**: two Heltec V4 boards running the identical image differ by one resistor, and only one of them can control its amplifier. So we keep the question. That means re-adding what upstream deleted and writing the board-side half ourselves for the five boards only Offband supports.

**The thing we need: a security fix.** Every Offband image shipped to date contains a flaw where a crafted radio packet can make the decryption routine write past the end of a buffer on the stack. It is reachable remotely, and one of the three affected paths is the group-channel path. Upstream fixed it, but **only in 1.18.0 — not in the 1.17.1 patch release** — so there is no small update that closes it. It comes with this base move, or it gets deliberately patched on its own.

**The thing that makes this update deceptively easy to under-scope.** 30 files conflict, which sounds like the whole job. It is not. Another **58 files are changed on both sides and merge silently**, and six of the real breaks are in those 58 — including the rewiring of two role files, the two board headers that quietly lose the amplifier methods, and seven board configuration files that quietly lose their low-battery boot protection. **A review that only looks at conflicts will miss all of it.** That is the single most important line in this document, and the merge plan gives those items their own work item (Group J) so they cannot hide.

Everything else is either genuinely safe or merely effortful, and §1 says which is which with the number behind it.

## 2. 🔴 SECURITY — `MACThenDecrypt` stack buffer overflow is in every shipped Offband image

**Our code, unpatched** `[verified: src/Utils.cpp:180-182]`:

```cpp
if (memcmp(hmac, src, CIPHER_MAC_SIZE) == 0) {
    return decrypt(shared_secret, dest, src + CIPHER_MAC_SIZE, src_len - CIPHER_MAC_SIZE);
}
```

**Upstream's fix** (`9c9a2ba2`, refined by `b74ba545` to run the check before the HMAC):

```cpp
int enc_len = src_len - CIPHER_MAC_SIZE;
if (enc_len % CIPHER_BLOCK_SIZE != 0) return 0;  // reject non-block-aligned ciphertext
return decrypt(shared_secret, dest, src + CIPHER_MAC_SIZE, enc_len);
```

**Upstream's own description of the defect:** `decrypt()` processes 16-byte AES blocks and rounds non-aligned
input up, so it "can write up to 8 bytes past the caller's stack buffer… triggered by crafted packets that
pass the 2-byte HMAC check (1-in-65536 chance per attempt), enabling a persistent denial-of-service attack
against repeaters and other nodes."

**Our exposure:** three call sites, all passing packet-derived lengths into a stack buffer —
`src/Mesh.cpp:158`, `:215`, and **`:242`, which is the group-channel path** (`channels[j].secret`).

### The attribution correction that changes the remediation

**It is not in 1.17.1. It is in 1.18.0 only.**
`[verified: git merge-base --is-ancestor 9c9a2ba2 d9296435 → false; …81dbae59 → true; …origin/firmware-base → false]`
Both commits are author-dated February 2026 but reached upstream's main line **after** our August base point —
the same author-date-is-not-merge-order trap as the bootlock commit (`3984b872`, author-dated 2026-04-22,
likewise not an ancestor of our base).

**Consequence: taking a patch release does not remediate this.** It arrives with the 1.18.0 base update, or it
is cherry-picked deliberately as a security patch — and since #613 puts routine cherry-picking out of scope,
that is an explicit owner decision either way.

### One severity nuance worth testing before anyone quotes the odds

Upstream's "1-in-65536 per attempt" assumes the attacker must *guess* the 2-byte HMAC. An attacker who
**knows the channel secret** — any well-known or public group-channel PSK — can compute a valid HMAC and craft
non-block-aligned ciphertext **deterministically**, making the trigger reliable rather than probabilistic on
that channel. `[hypothesis: untested — this follows from the code path, but no packet has been constructed, no
overflow measured, and the stack buffer size at each call site has not been checked]` That test does not change
the fix; it changes how urgent it is.

## 4. 🔴→🟡 `FIRMWARE_VER_CODE` — the headline collision, and how it resolves

| | Value | Source |
|---|---|---|
| Offband today | **22** | `examples/companion_radio/MyMesh.h:32` |
| Upstream 1.17.0 (our base) | **13** | `727fc051:examples/companion_radio/MyMesh.h:8` |
| Upstream 1.18.0 | **14** | `81dbae59:examples/companion_radio/MyMesh.h:7` |

**We did not collide by taking a number — upstream's numbering walked into a range we had already spent.**
`MyMesh.h:32` records the allocations: 18 (#508, second caps byte at offset 84), 19 (#510, caps2 0x01
NOTIFY_SCOPE), 20 (#509, caps2 0x02 BUTTON_MATRIX), 21 (#542, caps2 0x04 INDICATORS), 22 (#611, caps2 0x08
PKT_HASH). Upstream defined 14 on 2026-10-15, gating `CMD_RUN_CLI_COMMAND 66` and `RESP_CODE_CLI_REPLY 29` on
"v14+".

**Resolution: stay at 22.** Our client's gates are keyed on our allocations — Block ≥ 15, Caplog ≥ 17,
PktHash ≥ 22 — so lowering the number breaks every Offband client. And 22 ≥ 14 is *correct after this merge*,
because the merge delivers the v14 obligations: upstream's `CommonCLI` dispatch brings `CMD_RUN_CLI_COMMAND 66`,
and both 66 and `RESP_CODE_CLI_REPLY 29` are **free on our side**
`[verified: our commands are 0xC1/0xC3/0xC4/0xC5/0xC6; upstream's command max is 66]`.

**The exposure that exists today, before the merge.** We ship 22 right now while implementing none of
upstream's v14 features, because at our 1.17.0 base nothing upstream claimed 14. A stock client built against
1.18.0 reads our 22 as "v14+ present" and will offer the CLI path. **This base update closes that condition
rather than creating it** — an argument for the update, not a risk of it.

The structural fix for the whole registry is [#514](https://github.com/OffbandMesh/meshcore-firmware/issues/514),
still open: a prose table in a header comment cannot prevent this class of collision, and this is the second
release in which it has mattered. The client side is tracked at
[OffbandMesh/meshcore-client#857](https://github.com/OffbandMesh/meshcore-client/issues/857).

## 5. Where upstream's change is worse for us, and we keep our own path

**`EnvironmentSensorManager.cpp` — GPS detection.** Ours (#149) is a **non-blocking runtime auto-baud state
machine** driven from `loop()` on ESP32, deliberately performing no blocking probe at init, with
`gps_detected` meaning "a candidate baud yielded valid NMEA" — which is what the `0xC1` query reports to the
client. Upstream's change (their #2258) replaces a fixed 1 s delay with a **polling loop of up to ~5 s at
init**. Adopting it would reintroduce boot blocking, break the auto-baud design, and change the meaning of a
byte the client already consumes. **Keep ours.**

**`RadioLibWrappers.cpp` — noise-floor logging.** Ours (#1275) is a runtime throttle: the sampler completes
about twice a second and used to make ~90% of a tester's capture one repeated line. Upstream's is a
compile-time `#ifdef MESH_DEBUG_NOISE_FLOOR` gate, which cannot be turned off on a board already in a tester's
hands. **Keep ours.**

**Upstream's nRF52 bootlock removal.** `3984b872` strips `-D NRF52_POWER_MANAGEMENT` from 11 variant `.ini`
files; upstream's stated reason is that a fixed 3.3 V gate breaks LFP/LTO/SIB chemistries. **Not applicable to
our fleet** — `HARDWARE.local.md` records only LiPo and Li-ion. SafeBoot is armed on 3 of the 11
(`heltec_t096`, `sensecap_solar`, `xiao_nrf52`), so those stay gated. **8 lose their only boot-voltage gate:**
`gat562_30s_mesh_kit`, `gat562_mesh_evb_pro`, `gat562_mesh_tracker_pro`, `gat562_mesh_watch13`, `heltec_t114`,
`muziworks_r1_neo`, **`rak3401`**, **`rak4631`** — of which rak3401 ×2 and rak4631 ×1 are in the fleet.

Failure mode, verified rather than assumed: `NRF52Board::powerOff()` enters SYSTEMOFF, which needs a reset or
a configured wake source, so there is **no shutdown/boot loop**. What is lost is the clean refusal to boot
below 3.3 V (`boot_voltage_mv > 1000 && < voltage_bootlock`, `NRF52Board.cpp:202`); without it a power-cycle
on a depleted pack boots and browns out instead of refusing. **Cost to reject: one line kept per variant.**

## 6. What upstream got right, and what we inherit

### The structural improvement worth taking later

1.18 adds `virtual void loop()` to `MainBoard` — *"Lets a board feed its watchdog"* — wired into all four role
loops. `startWatchdog`/`feedWatchdog` are **Offband-original** (`efe7df96` #257, 2026-06-30; wired into the
repeater by `6a5bdfd9` #266 under an `NRF52_PLATFORM` guard; extended to ESP32 by `8dfe5618`/`3098de7b`
#518/#519), with **0 upstream occurrences at base, 1.17.1 and 1.18.0**. The nRF52-only guard was **ours**, not
upstream's. Upstream's own watchdog concept is `ExternalWatchdogManager` (5 files at every upstream rev,
untouched by this delta).

Their new hook is **structurally better than ours** and is the natural home for `feedWatchdog()`, removing the
per-`main.cpp` guard problem behind #1083. **Adopting it is a follow-up on its own merits, deliberately out of
the base update's scope.**

### Inherited fixes, quantified

| Fix | Why it matters |
|---|---|
| **Null-key channel sink** (`BaseChatMesh::searchChannelsByHash`) | an empty channel slot has an all-zero secret, so zero-PSK group traffic validated against it and foreign messages were delivered as that channel's. **Any node with a free slot was a null-key sink.** Security-relevant |
| **Command-buffer clamp** (repeater, room-server, secure-chat `main.cpp`) | `strlen(command)` could exceed `sizeof(command)` and the read loop then indexed past the buffer |

| `DISABLE_BLE_LED` build flag (nRF52) | relevant to our indicator work (`OFFBAND_CAP2_INDICATORS`) |

| `DisplayDriver::forceFullRefresh()` | e-ink full-refresh control (default no-op, harmless) |
| `T096 PIN_SPI1_MISO` (`49d9f9a8`, in 1.17.1) | fixes our open P1 #642 — one line, auto-merges, unverifiable on our bench since we own no T096 |

## 7. Bounded: ESP32 retained memory

Upstream adds a third `RTC_NOINIT` user (`_rtc_backup_time`, `_rtc_backup_magic`, magic `0xAA55CC33`) in
`ESP32Board.h`, and rewrites `ESP32RTCClock::begin()/setCurrentTime()/tick()` around `esp_reset_reason()` —
the same path CrashLog classifies reboots from. `ESP32Board.h` auto-merges.

Our three consumers each validate their own magic and fall back to fresh defaults:

| Block | Location | Magic |
|---|---|---|
| SafeBoot `PersistedState` | `src/SafeBoot.cpp:158` | `0x5AFEB007` |
| CrashLog ring header | `src/helpers/diagnostics/CrashLog.cpp:123` | `0xCAFEF00D` |
| CrashLog boot counter | same file | `0xB007C001` |

**Worst case: a one-time loss of the boot counter, the crash ring and the SafeBoot backoff on the first boot
after the update — detected and logged, never silent corruption.** Whether the layout actually shifts is a
link-time question answerable only by a map-file diff, and **the answer cannot make the outcome worse than that
bound**, so it does not gate the decision. Worth naming anyway: a crash-survival log that resets on firmware
update loses exactly the window you want after an update.

## 8. Client impact — stock compatibility is the constraint, not an afterthought

**The standing constraint:** the Offband client is **always stock-compatible**, with Offband features additive
on top. People run stock firmware with our app, and that has to keep working.

Two layers coexist, and the architecture work is keeping the boundary between them explicit:

- **Stock layer — must track upstream, release by release.** If upstream changes stock protocol or behaviour
  and the client ignores it, the app degrades for people on stock firmware. Caps-bit gating is irrelevant here.
- **Offband additive layer — caps bits stay, permanently.** SafeBoot, the watchdog, CrashLog and caplog cannot
  exist on stock firmware and need caps bits to be discoverable **regardless of what stock does**.

**Verified state today: 1.18 does not break the client's stock path.**

- `DEVICE_INFO` is **byte-identical** at 1.17.0 and 1.18.0 (82 bytes), so nothing shifts under our parsers.
- Our guards are **length-based**, so an 82-byte stock frame returns null and every Offband gate is correctly
  false `[verified: meshcore_connector.dart:6486-6510]`.
- An unrecognised `txt_type` — such as the new `TXT_TYPE_CLI_COMMAND = 3` — is logged and dropped
  `[verified: meshcore_connector.dart:7514-7519]`.
- Stock feature gates keyed on low version numbers remain correct.

**The gap is that no mechanism exists to notice when that stops being true.** 1.18's stock-facing additions —
the list a stock-compatible client would *weigh*, not must adopt:

| 1.18 stock-facing change | Why a stock user would notice |
|---|---|
| Node Discover UI (#3279) + hidden repeaters not discoverable when adverts off (#3538) | discovery results differ from the stock app's |
| Sensor telemetry push, subscribe/unsubscribe (#3402 / #3497) | a stock capability we would not surface |
| `tz.offset` (#3329) | timestamps / timezone handling |
| `reboot` / `poweroff` / `shutdown` (#3442) | node control the stock app offers |
| WiFi settings — `wifi.enabled`, `wifi.status`, `wifi.pwd` (#3357 / #3458) | configuration the stock app exposes |
| `CMD_RUN_CLI_COMMAND (66)` / `TXT_TYPE_CLI_COMMAND (3)` | **optional** for us to send; nothing breaks by not sending it |
| Stock app baseline moved to v1.50.0 | the reference users compare us against |

**So the architecture work is:** make the stock-vs-additive boundary explicit in the client, and give the stock
layer a per-release tracking step. Lives in `OffbandMesh/meshcore-client`.

## 10. What genuinely cannot be settled without a build

Exactly two things:

1. **The build itself** — which of the 6 auto-merging breaks surface as compile errors, and whether the full
   `ci-green` matrix is green. The predicted breaks are named with file and line in the merge plan.
2. **Whether RTC slow-memory layout shifts** — a map-file diff. Bounded by §7 either way.

**The remaining honest limits of this assessment:** no device test; our own `ui-new` port is sized as "port 4
callbacks" but not line-counted; `HARDWARE.local.md` was read for its section index and the battery-chemistry
question only; and the conflict hunks of `MyMesh.cpp`, `MyMesh.h`, `companion_radio/main.cpp`, `NodePrefs.h`,
