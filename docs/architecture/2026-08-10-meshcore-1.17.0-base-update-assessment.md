## 0. In plain terms, before the detail

MeshCore 1.17.0 changes **how a node stores its settings**. Today every node writes its settings as one long unlabelled blob of bytes on its internal filesystem — a file called `/com_prefs` where "the FEM RX gain setting" simply *is* byte number 291, with nothing in the file saying so. Upstream has replaced that with a labelled file, `/prefs.json`, where each setting is written next to its name.

That is a good change and it permanently kills a whole class of bug we have already been bitten by. But there is a catch that matters to us specifically:

**Offband and upstream each added their own settings to the end of that unlabelled blob, and we put them in a different order.** Byte 291 means "FEM RX gain" on an Offband node and "flood_max_unscoped" on an upstream node. Upstream 1.17.0 ships a one-time converter that reads the old blob and writes the new labelled file — and that converter uses *upstream's* byte order. If we adopt it unchanged, then on the first boot after the update, **every already-deployed Offband node silently converts its settings wrongly and then writes the wrong values down permanently.**

It is fixable, cheaply, and the fix is well understood. But it is the single thing that must not be missed, and it is invisible unless someone looks — the wrong values are all small plausible numbers, so nothing crashes and nothing logs an error.

```
byte:      290        291         292         293         294        295 ...
Offband:   rx_gain  fem_rxgain  fld_unscop  fld_advert  ui_led     ui_display, caplog…, syslog…  (ends 364)
Upstream:  rx_gain  fld_unscop  fld_advert  fem_rxgain  cad_enab   (ends 295)
                    ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^  ^^^^^^^^
                    three fields permuted                our LED flag read as
                                                         "enable CAD before TX"
```

## 4. 🔴 FINDING 1 — the prefs migration will silently corrupt deployed Offband nodes

**This is the finding that governs the whole update.**

### 4.1 What upstream did

`[verified: git show companion-v1.17.0:src/helpers/CommonCLI.h]` Upstream replaced the flat `struct NodePrefs` with `class NodePrefs : public ConfigSerializer` — a keyed, self-describing format written to `/prefs.json`, with nested sub-objects (`radio`, `bridge`, `gps`, `repeat`, `room`, `power`). New files `src/helpers/ConfigSerializer.{h,cpp}` arrive wholesale (we have no counterpart, so no conflict there) plus `test/test_config_serializer/`.

`[verified: git show companion-v1.17.0:src/helpers/CommonCLI.cpp]` The migration is one-way and automatic:

```cpp
void CommonCLI::loadPrefs(FILESYSTEM* fs) {
  if (fs->exists("/prefs.json")) {
    _prefs->loadSerial(file);            // new keyed format
  } else if (fs->exists("/com_prefs")) {
    loadPrefsInt(fs, "/com_prefs");      // LEGACY binary reader
    if (savePrefs(fs)) { /* fs->remove("/com_prefs"); commented out */ }
  }
}
```

On first boot after the update: read the old blob with the legacy reader, write the new keyed file. The old file is left in place (the removal is commented out), which is a small mercy — the original bytes survive for forensics/rollback.

### 4.2 Why it breaks us

The legacy reader uses **upstream's** byte order. Ours differs. `[verified: git show <ref>:src/helpers/CommonCLI.cpp, offset comments in both trees]`

| Offset | Offband `firmware-base` @ `5e15510e` | Upstream `companion-v1.17.0` | Result on migration |
|---|---|---|---|
| 290 | `rx_boosted_gain` | `rx_boosted_gain` | ✅ correct |
| 291 | **`radio_fem_rxgain`** | `flood_max_unscoped` | ❌ FEM RX gain → flood limit |
| 292 | `flood_max_unscoped` | `flood_max_advert` | ❌ shifted |
| 293 | `flood_max_advert` | **`radio_fem_rxgain`** | ❌ shifted |
| 294 | `ui_led_enabled` (#542) | **`cad_enabled`** | ❌ **LED flag → "CAD before TX"** |
| 295 | `ui_display_mode` | *(end of record)* | ❌ dropped |
| 296–297 | `caplog_enabled`, `caplog_level` (#562) | — | ❌ dropped |
| 298–361 | `syslog_host[64]` (#566) | — | ❌ dropped |
| 362–363 | `syslog_port` (#566) | — | ❌ dropped |
| **next** | **364** | **295** | |

Offset 291 was a deliberate 1.16.0 decision — the in-tree comment still says so: *"radio_fem_rxgain stays at offset 291 (its pre-1.16 offset) so existing Offband prefs files survive the 1.16.0 base-update."* That choice was right then and is precisely what diverges now.

### 4.3 Why it is dangerous rather than merely wrong

- **Silent.** Every mis-read value is a small integer that passes `constrain()`. Nothing crashes, nothing logs.
- **Persisted immediately.** The bad read is written straight into `/prefs.json`, so the corruption becomes the node's new truth on boot one.
- **`ui_led_enabled` → `cad_enabled` changes radio behaviour**, not just cosmetics: any node that had its status LED enabled would come back with hardware Channel Activity Detection before TX. `[hypothesis: untested]` — I have not measured the on-air effect of CAD-before-TX on our radio settings; that would need a bench test.
- **69 bytes of Offband settings vanish** — caplog and syslog config (#562/#566) are on the live patio repeater today.
- **Affects real deployed hardware**: patio repeater, the RAK4631 car node, `Strycher-WIO`, ST-P, the companion — anything carrying a `/com_prefs` written by an Offband build.

### 4.4 The fix (for the plan, not to implement now)

Bounded and well understood:

1. **Keep Offband's `loadPrefsInt()` offsets. Do not take upstream's.** The legacy reader must describe the bytes our nodes actually wrote.
2. **Add the Offband-only fields to `structure()`** so they round-trip in the keyed format — `ui_led_enabled`, `ui_display_mode`, `caplog_*`, `syslog_*`, plus a real `fem_rxgain` key (see §5.2).
3. **Keep `/com_prefs` on disk** (upstream already leaves it) so a bad migration is recoverable rather than terminal.
4. **Test on hardware before it ships**, with a real pre-update `/com_prefs` from a node carrying non-default FEM/LED/caplog/syslog values. This is a data-migration change to deployed devices — it earns a hardware gate of its own, not just a green matrix.

**Silver lining, and it is a real one:** after this migration, keyed storage means **fork-private settings can never again collide by byte offset with upstream's.** The recurring class of pain that produced the 1.16.0 offset-291 resolution disappears permanently. This finding is an argument for care in *how* we take 1.17.0, not an argument against taking it.

### 4.5 A layout detector is REQUIRED — two upgrade paths, two different readers

Two questions hide here. The first is already solved; the second is mandatory work.

**(a) New format vs old — already discriminated, by filename.** `[verified: CommonCLI::loadPrefs]` Upstream keys off existence: `/prefs.json` → keyed loader; else the legacy binary. Unambiguous, no work needed.

**(b) Legacy-Offband vs legacy-stock-MeshCore — REQUIRED.** There are two real upgrade paths and they need different readers:

| Upgrade path | Legacy file written by | Must be read with |
|---|---|---|
| **Stock MeshCore (<1.17.0) → Offband** | stock MeshCore | **upstream offsets** |
| **Offband (<MC 1.17.0) → Offband** | Offband | **Offband offsets** |

A build with one reader gets one of those two wrong. Reading a stock-written file with Offband offsets corrupts it exactly as badly as the reverse — which is this whole finding, applied in the other direction. Flashing Offband over stock MeshCore is an ordinary app-slot flash that **preserves the data partition**, so a stock-written prefs file survives into an Offband boot.

> **Correction for the record.** An earlier draft of this section justified detection with "cross-base flashes are routine — the T1000-E and Wio Tracker arrived on stock Meshtastic." That was wrong twice over: those conversions were **clean wipes**, and Meshtastic never writes these files at all — they are MeshCore files. Collapsing a fact about *Meshtastic* conversions into a claim about *MeshCore stock* conversions is what produced the error, and I briefly downgraded the detector to "optional" on the strength of it. It is not optional.

### 4.7 🔴 Record length ALONE is NOT a sound discriminator — historical Offband lengths collide with upstream's

An earlier draft of this section claimed the two record lengths were "71 bytes apart, no overlap," and therefore that length was a sound discriminator. **That was derived from comparing only the *current* Offband length (364) against upstream.** The fork's record has grown repeatedly, and files written by older Offband builds are still in the field.

`[verified: walked every commit touching src/helpers/CommonCLI.cpp on firmware-base and extracted the `// next:` end offset from each]`

| Offband record length | Landed | Commit |
|---|---|---|
| 291 | 2026-02-13 | `3621038b` |
| 292 | 2026-06-13 | `b1c57229` (rebrand) |
| **293** | 2026-06-06 | `5f6821bb` (flood.max.advert) |
| **294** | 2026-08-03 | `5a2f51ad` |
| **295** | 2026-08-03 | `222a8de3` (#542 `led` CLI) |
| 296 | 2026-08-03 | `e53512ef` (#542 display mode) |
| 298 | 2026-08-05 | `8fcbad86` (#561 caplog syslog forward) |
| **364** | 2026-08-09 | `c0ad6742` |

Against upstream's **293** (1.16.0) and **295** (1.17.0):

- **Offband 293 collides exactly with stock MeshCore 1.16.0 (293).**
- **Offband 295 collides exactly with stock MeshCore 1.17.0 (295).**

Two exact collisions. A length-only detector reads an Offband-written 293-byte file as stock and mis-assigns offsets 291–292 — the precise corruption this task exists to prevent. The 293-length Offband build was current from 2026-06-06 to 2026-08-03, roughly two months, so field files of that shape are plausible.

**This is not a refinement of the design; it invalidates the design as originally stated.** Length is a *necessary* input, not a *sufficient* one. Resolving it is the first work of #627, and the migration must not be implemented until it is resolved.

Design directions to evaluate (none yet chosen, none verified):
- **Fail closed on ambiguity** (see requirement 3 below) — mandatory regardless of what else is chosen.
- **Corroborating on-device evidence** — an Offband node carries Offband-only artifacts (observer NVS namespaces, caplog/syslog state, Offband-only files). Presence of those alongside a 293/295-byte record is evidence of an Offband writer. `[hypothesis: untested]` — not yet checked whether any such artifact is reliably present across all Offband roles and versions.
- **Field-plausibility cross-check** — parse under both hypotheses and reject the one producing out-of-range values. Weak on its own (all the contested bytes are small ints), but may break ties.
- **A version/magic marker** for files written from now on — helps future migrations, does nothing for files already written.

**Correcting the "once per device, ever" claim too.** That was also wrong. A **downgrade → re-upgrade** cycle breaks it: the upgrade migrates to `/prefs.json`; a downgrade to an older Offband build ignores that file and writes `/com_prefs` again; the user changes settings; the next upgrade sees `/prefs.json` exists and loads it, **silently discarding every change made while downgraded**. The migration must compare modification times of the legacy file and `/prefs.json` and refuse to silently prefer the older one.

**Requirements (revised):**
1. Detect per path, per filename. Length is an input, **not the sole signal** — see §4.7.
2. **Log the detected layout, the length, and the evidence that decided it**, every time (SAFELANE §6).
3. **Fail closed.** If the layout cannot be determined unambiguously, **do not migrate**: log at error level, leave the legacy file untouched, and run this boot on defaults so an operator must intervene. Do **not** fall back to either offset table — the earlier "default to upstream" rule was itself a corruption path for truncated or older-Offband files.
4. Retain the legacy file on disk after migration so a wrong choice is recoverable.
5. Compare mtimes: a legacy file **newer** than `/prefs.json` indicates a downgrade cycle — warn loudly and do not silently discard it.
6. Verify store **C** (observer NVS) is untouched by a migration.
7. Define and document an operator-facing **rollback/recovery procedure** for a node whose migration went wrong.

Two supporting facts:

- **Short reads already degrade gracefully.** Our in-tree comment documents it: *"For old SPIFFS files predating a field, `file.read` returns 0 bytes and the field keeps its in-memory default."* Mis-sizing short loses defaults rather than reading garbage.
- **The keyed format appears to tolerate unknown keys** — `ConfigSerializer` assigns only on `keyMatch`, so an unmatched key is parsed and dropped. `[hypothesis: source-read, not device-tested]` — read from source, not observed on hardware; needs a real test before we rely on it.

### 5.1 Implementation comparison — and why "adopt theirs" is a REGRESSION

> **Second correction.** On the strength of the provenance above I first recommended adopting upstream's implementation wholesale. **That recommendation was made from the headers alone and it was wrong.** Having diffed the implementation, the opposite is correct.

`[verified: diff <(git show origin/firmware-base:variants/heltec_v4/LoRaFEMControl.cpp) <(git show companion-v1.17.0:variants/heltec_v4/LoRaFEMControl.cpp)]`

The entire diff is Offband additions. Adopting upstream's file would delete all three:

Not reconstructible from code.

### 5.2 🐛 The `fem_rxgain` serializer bug — real, but **already reported and fixed upstream. Do not file it.**

`[verified: git show companion-v1.17.0:src/helpers/CommonCLI.h:84-85]`

## 9. Recommendation

**Take 1.17.0 — but as a planned, gated migration, not a routine base bump. Do not start the merge until the prefs-migration plan is agreed.**

Reasoning:

1. **The prefs rework is worth having.** It permanently ends the byte-offset collision class that has cost us twice. Taking 1.17.0 buys a structural fix, not just features.
2. **The FEM convergence is easier now than later.** Upstream's implementation is close enough to ours that reconciling is a rename plus a serializer fix. The longer both drift, the worse that gets.
3. **The risk is concentrated, identified, and bounded.** One finding (§4) carries nearly all the danger, and the mitigation is understood.
4. **Volume is manageable** — 1.9× the 1.16.0 conflict surface, on a cycle we have run successfully before with a written plan.

**Not recommended:** a fast merge to get to green. A green matrix would not catch §4 at all — the corruption only appears on a device with an existing `/com_prefs`, which CI does not have.

### 10.4 The principle this settles

We are not in the business of maintaining private forks of other people's hardware code — that is the #197 rationale (stay close to MeshCore so rebases stay cheap) applied at feature granularity rather than naming granularity.
