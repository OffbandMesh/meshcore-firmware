# RC32 tester diagnostic kit

For a RadioCore RC32 that will not boot. Everything here answers one question first:
**does the application start at all, and if not, how far does it get?**

Nothing in this kit tells you anything without an **external UART sniffer**. That is the point —
the RC32's own USB console is generated by the chip, so it dies with the chip and power-cycles
the board when you attach to it. Every log ever captured that way came from a boot that had
already succeeded (#702). UART0 survives the chip failing and does not reset it.

---

## Before you wire anything

Three questions, one minute each. They resolve most "won't boot" reports without a sniffer:

1. **Which file did you flash?** `-merged.bin` or the plain app `.bin`?
2. **Which address?** Merged goes at **`0x0`**. App-only goes at **`0x10000`**.
   *App-only flashed at 0 lands on top of the bootloader and will not boot — and it looks exactly
   like a bad build.*
3. **Which board?** RC32-**L62** (HT-RA62A LoRa) or RC32-**68** (HT-HC01_V2 Wi-Fi HaLow)?
   Only the **L62** is supported. A HaLow unit behaves exactly like a broken board.

You do not need to erase first — the flash tool erases what it writes. Do **not** erase before an
app-only flash; that removes the bootloader and leaves nothing to launch the app.

## What is in the kit

| | |
|---|---|
| `firmware/*-merged.bin` | full image, flash at `0x0` (first flash / clean slate) |
| `firmware/*-app.bin` | app only, flash at `0x10000` (keeps your settings) |
| `sniffer/rc32_uart_sniffer_v3_esp32_s3_wroom_1/` | sniffer sketch (ESP32-S3 WROOM-1) |
| `sniffer/capture.py` | host-side capture — timestamps, survives reconnects |

Three firmware variants, each built from the same commit as the shipped release **plus
instrumentation and nothing else**: `companion_radio_usb`, `companion_radio_ble`, `repeater`.

**Flash the one matching what was failing.** Matching the failure matters more than picking the
most instrumented build.

## Wiring the sniffer

Any spare ESP32 works. Two wires minimum; four if you want remote reset.

| RC32 | ESP32-S3 sniffer |
|---|---|
| pin 12 (U0TXD) | **GPIO16** |
| pin 20 (GND) | **GND** |
| pin 18 (RST) | **GPIO17** |
| pin 5 (BOOT) | **GPIO18** |
| — | sniffer TX not connected |

These are the pins the supplied sketch already defines. If you wire differently, change
`PIN_SNIFF_RX` / `PIN_RC32_RST` / `PIN_RC32_BOOT` at the top of the sketch to match — any free
GPIO works.

**Do not move these to GPIO19 or GPIO20.** Those are USB D−/D+ on an S3; driving them kills the
USB connection, and the symptom looks like the sniffer dying rather than a pin conflict. Also
avoid 0/3/45/46 (strapping), 26–37 (flash and octal PSRAM) and 43/44 (UART0).

**GND is not a formality.** Without a common reference the UART reads garbage or nothing, which
is indistinguishable from a dead board.

RST and BOOT are **open-drain: pulled low only, never driven high.** Both already have 10K
pull-ups on the RC32. The pins are parked high-impedance as the first statement in `setup()`, so
resetting or reflashing the sniffer can never hold the RC32 in reset.

### Arduino IDE settings

Board: **ESP32S3 Dev Module**. Set **USB CDC On Boot: Enabled** if plugged into the native USB
port, **Disabled** on the UART port. Getting this wrong gives a sketch that uploads cleanly and
prints nothing.

## Capturing

```
python capture.py --list                                        # find the sniffer's port
python capture.py --port COM16 --out rc32-boot.log              # capture (appends, never truncates)
python capture.py --port COM16 --out rc32-boot.log --queue RST  # remote reset, mid-capture
```

Send the resulting log back. That file is the artifact.

You do **not** need to enable caplog or run any CLI command first. These builds mirror the log
to UART0 regardless of whether capture is switched on, and the boot beacons are written before
any of that is initialised.

## Reading the output

The load-bearing line is **`APP:CTOR`**:

```
[BEACON] APP:CTOR -- earliest static ctor; bootloader + IDF startup COMPLETED
```

- **It appears** → the bootloader and IDF startup both completed. The fault is in C++
  constructors or `setup()`, and the following `setup:*` beacons show how far it gets.
- **It never appears** → the fault is at or before the bootloader's jump to the app. No
  application-level change can address that; read the ROM banner instead.

The ROM banner prints before any of our code and gives the reset cause:

```
rst:0x1  (POWERON)              power-on, or CHIP_PU (the RST button)
rst:0xf  (BROWNOUT_RST)         supply collapsed -- power problem, not firmware
rst:0x5  (DSLEEP)               deliberate deep sleep (low-battery hold)
rst:0x15 (USB_UART_CHIP_RESET)  host-tool reset
boot:0x8 / 0x9 (SPI_FAST_FLASH_BOOT)   strapping correct, booting from flash
```

Repeated `POWERON` about a second apart, with a `BROWNOUT_RST` among them, is a **power**
problem — a flat cell or a resistive connection — not firmware.

`[hb] SNIFFER-v3 alive ... rx_bytes=N` is the sniffer's own heartbeat. If `rx_bytes` stays at 0,
the sniffer is healthy and the **wire** is wrong. That distinction is the whole reason the
counter exists: silence is only evidence when the instrument is provably alive.

## Known issues in these builds

Both pre-existing, neither an RC32 regression, both already documented:

- **Battery indicator reads high** (#780) — roughly 25 points optimistic through mid-discharge,
  and it cannot reach 100% on a full cell. The device also powers off while it still shows ~33%.
- **A low-battery hold looks like a dead board** (#782) — and connecting power does not end it;
  it wakes on its own timer, up to 10 minutes later.
