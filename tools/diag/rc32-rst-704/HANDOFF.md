## The problem, stated precisely

With **`heltec_rc32_companion_radio_usb`** flashed, pressing RST leaves the board dead —
no display, no radio, no BLE, no serial. With **`heltec_rc32_repeater`** flashed, RST
recovers reliably, repeatedly. Recovery from the companion state requires a **slow**
unplug/replug; a **fast** replug also fails.

---

## HARD FACTS (measured, trust these)

1. **On a companion RST the application runs ZERO times.**
   `nvs_count` (NVS-backed, one increment per `heartbeatBegin()`) went **89 → 90** across
   *one RST press plus one serial attach*. The attach alone accounts for the +1.
   Measured twice, second time on the current build. **This is the load-bearing fact.**

2. **`nvs_count` increments AFTER `board.begin()`**, not at the top of `setup()`.
   The two earliest `CW_PHASE` markers never appear in any trace because the retained-RAM
   ring is not yet initialised when they fire. So "zero increments" means
   **execution never got past `board.begin()`** — NOT "setup() never started."
   (I overstated this as "setup ran zero times." Corrected.)

3. **The app is healthy when it does run.** Full phase trace to `setup:DONE`, with
   `post:display.begin(OK)`. Nothing wrong downstream.

4. **Attaching to the RC32's USB console POWER-CYCLES the board** (`reset_reason=1 POWERON`,
   retained RAM wiped). This destroyed the evidence on every attempt — the act of
   observing is the act of fixing. Any "the board booted fine" observation from a
   serial attach is an artifact.

5. **The RC32's console is native USB-Serial-JTAG** — generated by the chip itself. When
   the chip fails to boot the COM port disappears with it, so **every log we captured was
   necessarily from a boot that SUCCEEDED.** We have never observed a failed boot.

6. **Our variant vs upstream MeshCore** (`git diff upstream/main -- variants/heltec_rc32/`):
   the ONLY deltas are `ENV_INCLUDE_GPS=0`, `DISPLAY_ROTATION=0`, `SAFE_BOOT_DISABLED`,
   and removal of `UI_HAS_ROTARY_INPUT`. **`boards/heltec-rc32.json` is byte-identical
   to upstream.** The variant is not where the problem lives.

7. **Vendor schematic facts** (`resource.heltec.cn/download/RadioCore/RC32/`):
   - RST button **S1 wires directly to ESP32-S3 CHIP_PU/EN pin 4**, via R31 10K pull-up
     and **C32 1 µF**. Net `CHIP_PU` has exactly six members
     (`C32.2, P1.18, P3.18, R31.2, S1.1, U8.4`) — **no PMIC, supervisor, GPIO or transistor.**
     So RST is a *true full-chip reset*.
   - USR button **S2 → GPIO0** (boot-mode strap), 10K pull-up, 100nF debounce.
   - Header pinout (Table 2.1.2): **pin 12 = U0TXD/GPIO43**, **pin 11 = U0RXD/GPIO44**,
     **pin 5 = GPIO0/USER**, **pin 18 = RST**, **pins 1/3/20 = GND**, pin 19 = 3V3.

## BEST OPEN LEAD (vendor-sourced, unverified)

Heltec's RC32 datasheet §3.2.1 lists these pins for **RC32-L62 (HT-RA62A LoRa)**:

```
GPIO23 SPI_CS   GPIO22 SPI_MOSI  GPIO21 SPI_CLK   GPIO20 SPI_MISO
GPIO19 DIO1     GPIO7  SELECT    GPIO8  RESET_N   GPIO10 BUSY
GPIO11 VEXT_LDO_Ctrl
```

Our variant (inherited from upstream, unmodified):

```
NSS=10  MOSI=12  SCLK=11  MISO=13  DIO1=14  RESET=9  BUSY=1
```

**These do not match.** Notably Heltec calls GPIO11 `VEXT_LDO_Ctrl` — a power-control line —
where we drive SCLK. The radio demonstrably works (road test, real packets), so either the
table uses module-side numbering or describes another revision. **Verify against the
RC32-L62 schematic before acting.** This is the only vendor-sourced discrepancy found.

## NEXT STEP — see the layer we've never seen

The ROM bootloader prints `rst:0x… boot:0x…` before any firmware exists. The `boot:` field
names the mode the **strapping pins actually selected** — which decides whether the app ever
gets a chance to run. We cannot read it over the RC32's own USB (it dies with the chip), so:

**External UART sniffer, already wired:**
- RC32 **pin 12** (U0TXD/GPIO43) → Feather **RX**
- RC32 **pin 20** (GND) → Feather **GND**
- Feather TX **not connected**

Sketch (heartbeat + `rx_bytes` counter, BUILD ID `SNIFFER-v2`):
`scratchpad\rc32_uart_sniffer\rc32_uart_sniffer.ino`

**Use Arduino IDE, not PlatformIO.** I burned two attempts on the Feather's USB config
(`ARDUINO_USB_CDC_ON_BOOT` vs `ARDUINO_USB_MODE`) — `Serial` landed on the TinyUSB CDC
peripheral while the enumerated port was USB-Serial-JTAG, so it flashed and verified but
printed nothing. Arduino IDE handles the Feather's USB setup correctly out of the box.

**Truth table once the heartbeat is confirmed:**

| Feather shows | Meaning |
|---|---|
| no `[hb]` | reader not running — fix that first |
| `[hb]`, `rx_bytes=0` | reader fine, nothing on the wire — wiring/pin |
| `[hb]`, `rx_bytes` rising, garbage | wire good, baud mismatch |
| `[hb]` + `[rc32-probe]` lines | **wire proven** — only now is RST meaningful |

**Likely complication:** the ESP32-S3 ROM *auto-selects* its console. With USB enumerated it
may route boot messages to USB-Serial-JTAG and leave UART0 silent. If so, power the RC32
**without USB** (VBAT pin 2 or 5V pin 4) so the ROM falls back to UART0.
(I earlier called the UART0 banner "hardwired" — that was wrong.)

To prove the wire before pressing RST: an uncommitted `-D OFFBAND_UART0_PROBE` build exists
in the worktree that TXs a marker on GPIO43 at boot and every 2 s.
